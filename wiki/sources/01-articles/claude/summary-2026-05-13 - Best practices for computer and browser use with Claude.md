## Core Summary

This Anthropic engineering blog post (authored by Lucas Gonzalez and Luca Weihs) compiles production best practices for building [[ComputerUse|computer use]] and browser-use integrations with the Claude 4.6 family (Opus 4.6, Sonnet 4.6, Haiku 4.5) and Claude Opus 4.7, alongside a companion demo implementation (`computer-use-best-practices` on the `anthropic/claude-quickstarts` GitHub repo). It covers five areas: (1) click accuracy, driven overwhelmingly by pre-downscaling screenshots to the API's internal resolution limits before sending them, plus practical mitigations for small UI targets (zoom, larger targets, keyboard alternatives); (2) [[AdaptiveThinking|adaptive thinking]] effort-level tuning for computer use, finding `medium` effort is the general sweet spot and `low` effort is surprisingly strong for cost-sensitive workloads, while `max` effort provides no benefit; (3) [[PromptInjection]] defenses, describing three complementary layers (training-time RL robustness, real-time classifiers, continuous red-teaming) that run automatically and at no extra cost for the official `computer_20251124` tool type but not for custom tool definitions, plus recommended human-in-the-loop and permission-scoping practices; (4) long-horizon context management combining [[PromptCaching|prompt-cache]] breakpoint placement, batched screenshot pruning (rolling buffers), and prompt-driven compaction (including the new server-side `compact_20260112` beta tool), plus emerging patterns — `computer_batch`/`browser_batch` tool calls, the [[AdvisorStrategy|advisor tool]] paired with a mechanical executor model, and periodic reminder nudges for underused tools; and (5) "Teach Mode" — recording a human demonstration (screenshots, selectors, coordinates, optional voice narration) as a reusable workflow specification that Claude replays adaptively rather than via strict coordinate replay, used internally in [[ClaudeInChrome]].

## Key Points

- **Downscaling is the single highest-impact fix for click accuracy.** The Computer Use API silently downscales images that exceed internal limits before the model sees them, but returns coordinates in the *display* space the developer specified — a mismatch that is "the primary cause of click inaccuracy at high resolutions."
  - Claude 4.6 family limits: max long edge 1568px, max pixel budget ~1.15MP.
  - Claude Opus 4.7 supports higher resolution: max long edge 2576px, max pixel budget ~3.75MP.
  - **Start with 1280x720** as a safe default (~80% of the 4.6-family pixel budget); **start with 1080p for Opus 4.7**.
  - A "max API fit" approach (code provided) computes per-image optimal resolution preserving native aspect ratio, avoiding the distortion of forcing a 16:9 source into a 4:3 display size — modest accuracy gain over fixed 720p.
  - Developers must scale API-returned click coordinates back to native screen resolution before executing (`scale_x = screen_w / display_w`, etc.); a persistent offset results if this scaling or the declared `display_width_px`/`display_height_px` don't match reality.
  - Place the text instruction *before* the image in the content array (improves click accuracy vs. image-first ordering).
- **Model comparison for clicking**: Sonnet 4.6 is more mechanically precise (fewer near-misses) and more robust to heavy downscaling; Opus 4.6 has stronger reasoning. Opus 4.7 narrows the precision gap — roughly on par with Sonnet 4.6 — while its higher resolution budget reduces how much downscaling is needed. Recommendation: Sonnet 4.6 for most tasks (best balance); Opus 4.7 for harder reasoning tasks or high-resolution sources; Haiku 4.5 when latency is the priority; an orchestrator (reasoning model) + Sonnet/Haiku (mechanical clicking) sub-agent pattern for advanced workflows.
- **Small-target mitigations**: enable `enable_zoom: True` on the `computer_20251124` tool for dense UIs; enlarge click targets (lower DPI, browser zoom, UI scaling) where the developer controls the UI; prefer keyboard shortcuts/tab navigation for tiny targets (system tray icons, tiny checkboxes); prefer Opus 4.7 or lower-DPI capture for 4K+ source displays (example given: a 16px checkbox at 3840x2160 becomes ~5px at 1280x720).
- **Some failures aren't about clicking at all** — e.g., system-level UI (like certain dropdowns) that the browser viewport can't capture; the fix is to use JavaScript execution, keyboard navigation, or direct DOM manipulation instead of clicking.
- **Adaptive thinking effort levels for computer use** (`thinking={"type": "adaptive"}`, `output_config={"effort": ...}`, levels: low/medium/high/xhigh [Opus 4.7 only]/max), tested on OSWorld Verified and a suite of end-to-end UI automation tasks:
  - Opus 4.7 outperforms the entire 4.6 family at equivalent token usage/effort; Opus 4.7 at `low` effort scores similarly to Sonnet 4.6 at `max`, using ~1/10th the tokens.
  - `medium` effort achieves close to the highest task success rate using roughly half the output tokens of `high`; performance plateaus beyond `medium`, and with retries, `medium` and `high` converge to similar success rates.
  - `low` effort is a surprisingly strong, low-cost option — it uses *fewer* total output tokens than disabling thinking entirely (fewer mistakes → fewer retries) while matching or slightly exceeding no-thinking accuracy, making it best for cost-sensitive, high-throughput workloads.
  - `max` is explicitly **not recommended**: no accuracy benefit over `high` in testing, since UI tasks are primarily perceptual rather than deeply logical.
- **Prompt injection defenses (three layers)**: (1) training-time RL robustness — Claude is exposed to injected content in simulated pages/UIs during training and rewarded for refusing; (2) real-time classifiers — probes scanning content entering the context window across modalities (hidden text, image-embedded instructions, deceptive UI), running in parallel with inference at ~zero added latency/cost; (3) continuous red-teaming, including participation in external adversarial evaluations.
  - Classifiers run **automatically and for free** when using the official `computer_20251124` tool type — no configuration needed.
  - Classifiers do **not** currently run for custom/self-defined computer-use tool implementations; Anthropic is exploring extending this and is collecting interest via a form.
  - Recommended layered practices regardless of classifiers: human-in-the-loop confirmation before irreversible actions (submitting forms, purchases, sending messages) — called "the single most effective mitigation against prompt injection regardless of classifier performance"; scope/limit agent permissions to reduce blast radius; log full action sequences and screenshots for auditing; treat all encountered web/application content as untrusted, distinct from user instructions, in the system prompt.
- **Context management for long-running computer-use agents** — screenshots consume ~1,000–1,800 tokens each; a 200K context window can fill in well under 100 screenshots. Three composable layers:
  - **Cache breakpoints**: the API supports 4 total; put 1 on the stable prefix (system prompt/tool defs) and reserve the other 3 for recent history (highest invalidation risk, highest savings). Spreading breakpoints across recent positions gives graceful degradation — if the newest breakpoint is invalidated, an earlier one can still hit (paying 10% of full input cost instead of 100%).
  - **Rolling buffer / batched pruning**: keep only the N most recent screenshots, replacing older image blocks with a text placeholder (`"[Image omitted]"`). Naive one-at-a-time pruning invalidates the cache every turn; the fix is to prune in *batches* so the prefix stays byte-identical for an interval of turns. Suggested defaults: `keep_n=3`, `interval=25`. Rolling buffers lose everything outside the buffer (original instructions, prior attempts, task position) — fine for short tasks (<~50 actions), otherwise combine with compaction.
  - **Compaction**: summarize the full conversation before discarding it rather than silently dropping images; keep a few recent screenshots alongside the summary. A detailed `COMPACT_PROMPT` template is given with mandatory sections: User Instructions (verbatim), Task Template (for repeatable workflows), Constraints and Rules, Actions Taken, Errors and Fixes (to avoid retrying failed approaches), Progress Tracking, Current State, Next Step.
  - **Server-side compaction (beta)**: `compact_20260112` in `context_management.edits`, gated behind beta header `compact-2026-01-12`; developers pass their own summarization prompt via the `instructions` parameter (fully replacing the default) and a `trigger.value` input-token threshold; `pause_after_compaction` keeps recent messages (including screenshots) attached across compaction events. Because the server drops pre-compaction content on its side but the client's local array still holds full history, developers must mirror the truncation locally (drop messages before `message_index_after_compaction` from the `applied_edits` compaction record) to keep the client/server views — and the rolling-buffer pruner — aligned.
- **Emerging / experimental patterns** (not yet blanket recommendations):
  - **`computer_batch` / `browser_batch` tools**: custom tool definitions that bundle multiple sub-actions (click, type, press key) into a single tool call/round trip, reducing wall-clock time and output tokens on long-horizon tasks. Recommended only for self-contained sub-actions that don't depend on each other's visual outcomes (e.g., filling multiple form fields); avoid for exploratory navigation or error-recovery sequences where a single failed action should trigger re-planning. Stack cleanly alongside the standard computer/browser tools — the model chooses.
  - **Advisor tool** (`advisor_20260301`, beta header `advisor-tool-2026-03-01`) for computer use: pairs a mechanical executor model (e.g. Sonnet 4.6) with a higher-intelligence advisor (e.g. Opus 4.7) consulted mid-generation for planning/course-correction moments (choosing a tab, recovering from an unexpected modal, deciding whether to abandon a strategy), server-side, in a single request. The advisor runs without tools and without context management — it can't click or browse, only returns text advice. If the advisor tool is later dropped from the tools array (cap hit, config change, model switch), prior `server_tool_use`/`advisor_tool_result` blocks become orphaned and cause a 400 error on the next request unless stripped first (code provided: `strip_orphaned_advisor_blocks`).
  - **Reminder nudges**: on long sessions the executor can forget which tools are available. A short system-level nudge after a tool result can re-surface underused `computer_batch`/`browser_batch` tools; a ~20-turn cadence reminder can re-surface an unused advisor tool. Both are light-touch (a few tens of tokens) and should be weighed against added cache-invalidation risk if cache breakpoints are precisely placed.
- **Teach Mode** (used internally in [[ClaudeInChrome]]): instead of iterating on text prompts, a user records themselves performing a task (screenshots, actions, optional voice narration at each step); the recording becomes a reusable specification Claude replays as context, adapting to live UI differences rather than blindly replaying recorded coordinates.
  - Core data model: a `WorkflowStep` (action type, description, timestamp, optional CSS selector/XPath, coordinates, URL, base64 screenshot annotated with a click marker, viewport dimensions, voice transcript, typed value) composed into a `SavedWorkflow` (id, name, ordered steps, AI-generated description, start URL, usage count). Selectors are robust to layout changes; coordinates are a visual fallback; both plus viewport dimensions are captured so coordinates can be rescaled if playback environment differs from recording environment.
  - Playback message = user's new-task prompt + a `<demonstration_context>` block (explaining that blue circles are recording annotations, not live UI, and instructing Claude to take its own screenshot, find the equivalent element, and adapt to differences) + each step's screenshot as an image, with step descriptions interleaved as text.
  - **Strictness parameter** (three modes): **Strict** — follow steps exactly, stop and report if the UI changed too much (compliance-sensitive workflows); **Adaptive** — best default; use the demonstration as a guide but adapt to layout shifts/relabeled buttons/reorganized menus; **Goal-oriented** — treat recorded steps as hints, focus on end result (for frequently-changing UIs); use a summarization model over the recording similar to the compaction section's approach when the workflow is too long for direct context inclusion.
  - Worked example given: a 5-step "Submit Expense Report" workflow (navigate, open dropdown, select "Travel", enter amount, click Submit) later replayed for a new request ("Submit my expense report for the team lunch ($85.50)") with Claude adapting the amount/description values while following the same click sequence.
- **Anomaly note**: no prompt-injection-style embedded instructions (e.g., "Hi Claude, please...") were found in this raw source file during ingestion.
