## Core Summary

This April 2026 Anthropic blog post is a direct sequel to "Building multi-agent systems: when and how to use them" ([[summary-2026-01-23 - Building multi-agent systems When and how to use them]]): once a team has decided multi-agent is worth the overhead, this post covers which *coordination pattern* to use. It defines five patterns — generator-verifier, orchestrator-subagent, agent teams, message bus, and shared state — each with its mechanics, an illustrative production scenario, and specific failure modes, arranged roughly along a spectrum from centralized/bounded to decentralized/autonomous. The post's central recommendation is to start with the simplest pattern (orchestrator-subagent), observe where it strains, and evolve toward a more complex pattern only when a specific limitation demands it; patterns are framed as composable building blocks rather than mutually exclusive choices.

## Key Points

- **Generator-Verifier**: a generator produces output, a verifier checks it against explicit criteria and either accepts or returns feedback for revision; loops until acceptance or a max-iteration cap. Broader framing of the "verification subagent" pattern from the prior post (generator need not be an orchestrator). Best for code generation, fact-checking, rubric grading, compliance checks. Failure modes: an underspecified verifier rubber-stamps output; if generation and evaluation require the same skill, the verifier can't reliably catch problems; unresolvable feedback loops oscillate without a max-iteration/fallback (escalate to human, return best attempt with caveats).
- **Orchestrator-Subagent**: a lead agent plans, delegates bounded subtasks to subagents, and synthesizes their results (Claude Code's own architecture is given as the example — subagents run in isolated context windows and return distilled findings while the main agent keeps editing/running commands). Best when task decomposition is clear and subtasks have minimal interdependence. Failure modes: the orchestrator becomes an information bottleneck when one subagent's finding is relevant to another's work; sequential (unparallelized) execution incurs multi-agent token costs without a speed benefit.
- **Agent Teams**: a coordinator spawns multiple worker agents ("teammates") that claim tasks from a shared queue and work autonomously across multiple steps, unlike orchestrator-subagent where a subagent is dispatched for one bounded task and terminates. The distinguishing axis is **worker persistence** — teammates accumulate context/domain specialization across assignments. Example: migrating each service of a large codebase independently. Failure modes: teammates can't easily share intermediate findings (conflicting outputs if one teammate's work affects another's), completion detection is hard (variable per-teammate duration), and shared resources (same codebase/DB/filesystem) can produce conflicting concurrent edits.
- **Message Bus**: agents publish/subscribe to topics through a shared router; new agent capabilities can join without rewiring existing connections. Example: security-operations triage routing alerts to specialized investigation agents. Best for event-driven pipelines with a growing agent ecosystem. Failure modes: harder to trace/debug than an orchestrator's sequential decisions; a misrouting or dropped event fails silently (LLM-based routers add semantic flexibility but their own failure modes).
- **Shared State**: agents read/write a persistent shared store directly with no central coordinator; work starts when an initialization step seeds the store and ends at a termination condition (time limit, convergence threshold, or a designated agent judging the store "sufficient"). Example: research synthesis where independent investigator agents (academic literature, industry reports, patents, news) see each other's findings immediately. Removes the coordinator as a single point of failure, but sacrifices predictability: duplicate work (fixable via locking/versioning/partitioning) and **reactive loops** (agents ping-ponging on each other's writes without converging — the hardest failure mode, requiring first-class termination conditions rather than an afterthought).
- **Choosing/evolving**: orchestrator-subagent vs. agent teams turns on how long workers need to retain context; orchestrator-subagent vs. message bus turns on how predictable the workflow structure is (message bus wins as conditional routing logic grows); agent teams vs. shared state turns on whether workers need to communicate with each other, not just report final results; message bus vs. shared state turns on whether a central router is acceptable (message bus still has one single point of failure; shared state is fully decentralized). Production systems commonly hybridize (e.g., orchestrator-subagent overall with a shared-state sub-collaboration; message bus for routing with agent-team-style workers per event type).
- **Recommendation**: default to orchestrator-subagent — widest applicability, least coordination overhead — and evolve only as specific limitations surface.
