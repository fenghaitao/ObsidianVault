## Definition

Thariq Shihipar is an engineer at Anthropic on the Claude Code team, interviewed by Ryan L. Peterman about how Anthropic builds software with frontier models and how engineering will change.

## Key Information

- Works on the Claude Code team at Anthropic; the conversation centers on getting the most out of models for software engineering.
- Before Anthropic, did an applied-research fellowship at Good Fire, an AI interpretability company, exploring how to use interpretability to make better products.
- His first model was GPT-2; he recalls how hard it was just to get useful JSON/category output from it, and says that grounding still transfers to working with today's frontier models.
- Got his Anthropic job as a "luck surface area" example: he built and publicly shared an interpretability visualization from the Good Fire project (his first big Twitter post, ~500 likes), which led to DMs and eventually an intro into a role at Anthropic.
- Number-one onboarding tip for people inside and outside Anthropic: treat Claude like a thought partner and give it the context you need; start from "Can Claude do it? If not, why not?"
- Frames the model-vs-harness relationship: models improve, but the harness (auto mode, sandboxing, artifacts, workflows) must grow more complex to unlock what the models can do.
- Draws a working split between Claude Code (implementation of code) and "Claude Tag" (tagging Claude for the rest of the software development life cycle).
- Practical prompting habits: give the model permission to use compute, subagents, and workflows; to brainstorm before producing; and to treat a hard problem as license to spend compute ("believe in yourself" really means permission to use compute).
- On AI-written prose: disclosure rule of thumb — "if I would be happy to show someone the prompt, I would send them the output"; routine data readouts can be AI-generated (reviewed), but novel thought and essays stay human-written.
- Argues being technical still matters despite "coding is largely solved": the only way to tell you've built great software is to be a great software engineer.
